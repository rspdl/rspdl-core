# E03 비공개 평가 기준 — 시설 점검 보고서 등록·정정·인계

이 문서는 생성기에 제공하지 않는다. `input.md` 전체가 하나의 제품 평가 단위다. 요구별 판정과 세 사람용 검토 여정은 그 한 제품의 누락·의미 변형을 찾는 관점이며 독립 과제나 실행 테스트가 아니다. 정답 RSPDL, 테스트 코드, 참조 구현을 제공하지 않는다.

지원 기준 HEAD: `837290a83911e160f27835f246a5bd7df21107b1`. 작업 중인 다른 실험 문서나 과거 gold/reference는 근거로 사용하지 않았다. 아래 문법 근거는 이 HEAD의 현재 구현과 conformance를 기준으로 한다.

## 판정 방식

공통 `public-contract.md`와 `judge-instructions.md`를 따른다. 각 R ID에 대해 생성 문서의 인용 가능한 선언·문장·설명을 기록하고 `충족 / 위반 / 판정 보류`로 판정한다. 필수 사실이 일부 빠졌거나 반대 내용이 있으면 위반이며, 해석상 실질적인 쟁점이 있을 때만 보류한다. 단순히 행동이나 화면의 이름이 있다는 것으로 충족하지 않는다. 한 요구의 세부 사실을 아래 표의 쉼표 단위로 확인하고 빠진 사실을 기록한다. 평가는 두 실험군 모두 최종 한국어 제품 명세만을 대상으로 한다. 아래 Can/Cannot/DoAttempt, Read/Update/Delete, binding, producer 등은 업무 의미와 지원 근거를 설명하는 약칭이며 최종 산출물에 해당 RSPDL 구문이나 특정 표기법을 요구하지 않는다. 중간 RSPDL이나 compiler 로그에만 있는 사실에는 최종 명세 점수를 주지 않는다. 문법 성공 여부와 별개로 저자의 업무 의미를 사람이 판정한다. 컴파일 결과를 얻는 경우에도 권한·조건의 논리적 진실성이나 실제 변경 성공의 증거로 삼지 않는다.

중요도 C는 핵심 권한·변경·출처·완료 계약, M은 제품 구조·정보 보존이다. 중요도는 영향 설명이며 가중 점수를 주지 않는다. C의 위반은 제품 핵심 실패로 별도 표시한다. R18/R19의 잘못된 대상 변경, R23의 제한 자료 공개, R26/R27의 사건 자료 변경, R25/R40의 실행 보장 주장은 개별 보고한다. 임의 숫자 임계치나 숨은 요구는 추가하지 않는다.

## 사람이 따라 읽는 여정 1 — 체육관 보고서를 등록하고 정정 후 인계하기

문서만 읽으면서 다음 합성 입력을 해당 행동·화면·field 출처에 대입한다. 서버나 브라우저를 실행하지 않는다.

1. 초기 시설은 `F-17 / 서안체육관 / 운영중=true`다. 점검담당자가 시설 선택→작성에서 `보고서번호=IR-2401, 작성부서=시설관리팀, 본문=출입문 경첩 느슨함, 점검일=2026-10-19, 작성일=2026-10-19, 결과=보수필요, 열람제한=false`를 등록한다. 문서가 두 시설 field의 초기 전제, 일곱 입력의 등록 버튼 획득, 보고서 초안 생성 출처, 완료 화면의 아홉 필수 데이터를 연결하는지 확인한다. 같은 날 작성이 정상이어야 한다.
2. 목록→상세에서 담당자가 보고서를 조회하고 제출한다. 조회의 Read와 제출의 상태 변경 시도를 구별한다. 검토담당자는 `요청번호=CR-31, 요청일=2026-10-19, 사유=조치 계획 추가, 요청종류=내용보완`로 정정 요청한다. 요청의 보고서번호가 선택 보고서에서 와야 하며 요청 상태/회신은 대기/미처리, 보고서는 이 등록만으로 정정대기가 되지 않는다. 이어 두 기존 기록을 명시적으로 전달해 정정 개시하면 세 조건을 확인하고 보고서 정정대기 변경을 시도하는지 확인한다.
3. 점검담당자에게 `보고서 IR-2401`과 `요청 CR-31(보고서번호 IR-2401, 상태 대기)`를 각각 전달한다. `새 본문=경첩 보수 예정, 새 결과=보수필요, 회신=계획 반영`으로 반영한다. 문서에서 세 조건의 AND, 두 기록의 Read, 보고서 본문·결과·상태와 요청 상태·회신의 다중 필드 수정 시도를 찾는다. 동일 기록의 서로 다른 field 수정은 정상 의도다.
4. 검토담당자가 `인계번호=HO-44, 받는부서=시설운영팀, 인계일=2026-10-20, 회신기한=2026-10-22, 인계방식=부서전달`로 발행한다. 인계증은 먼저 초안으로 생성된다. 완료 화면에서 보고서와 이 인계증을 명시적으로 전달해 인계 확정할 때 세 조건을 확인하고 보고서 인계완료/인계증 발행 변경 의도가 필요하다. 인수담당자는 전달된 HO-44를 조회하고 `회신일=2026-10-22, 접수메모=운영팀 접수`로 접수할 수 있어야 한다. 기한 당일이 허용이고 발행→접수·메모 변경 시도다.
5. 사건 `전송 접수 통지(기존 자료=RC-91/IR-2401/운영팀 외부함/2026-10-22, 처리결과=수신)`을 읽는다. 시스템이 이 자료를 읽으려는 의도와 수신 안내 하나의 field 출처를 확인한다. 이 사건이 인계증을 접수 상태로 변경했다는 문장은 없어야 한다.

주요 coverage: R01–R14, R16–R18, R20–R22, R25–R38, R40–R42. 예상 증거는 생성 문서의 명시적 입력·조건·effect·producer·레이아웃·workflow 선언이다. “실행해서 저장된 결과”는 예상 증거가 아니다.

## 사람이 따라 읽는 여정 2 — 잘못 전달된 정정 요청을 되돌리고 반려하기

1. 보고서 `IR-2402(정정대기)`와 요청 `CR-32(보고서번호=IR-9999, 상태=대기)`를 점검담당자에게 별개 입력으로 준다. 반영은 번호 불일치로 금지여야 한다. 문서에 대상 자동 재검색이나 “같은 시설이면 반영” 같은 보정이 없어야 한다. 금지 선언을 실제 요청 삭제·실행 완료로 읽지 않는다.
2. 호출자가 올바른 `CR-33(보고서번호=IR-2402, 요청종류=오기정정, 상태=대기)`를 다시 공급한다. 검토담당자는 `회신=기존 본문 유지`로 반려할 수 있다. 보고서는 제출 상태로 돌아가고 요청은 반려/해당 회신으로 바꾸는 의도여야 한다. 본문·결과가 반영 입력으로 덮이지 않아야 한다. 반려 뒤 새 요청을 하려면 새로운 정정 요청 등록 행동을 사용한다. 자동 재시도·자동 복구·과거 요청 재활성화는 없다.
3. 다른 초안 `IR-2403`에서 담당자가 새 본문·날짜·결과·열람제한을 저장하는 경로와, 삭제하여 목록으로 돌아가는 경로를 각각 읽는다. 수정은 다섯 field이고 삭제는 대상 Delete다. 삭제 처리에 같은 대상 Read가 함께 없어야 한다. 제출된 IR-2402의 초안 수정·삭제는 금지다.
4. 외부 사건에 `처리결과=거절`, 자료 `RC-92/IR-2402/운영팀 외부함/2026-10-22`를 준다. 안내 하나와 "RC-92: IR-2402 / 운영팀 외부함"의 조합 출처 및 처리결과=거절 저장을 확인한다. 거절 사건 때문에 보고서 상태를 되돌리거나 외부 전송을 재시도하지 않는다.

주요 coverage: R04, R11, R14–R19, R24–R28, R31–R34, R37, R40. 문서의 실패 조건과 정상 재입력 경로를 함께 검토한다. “오류 메시지 문구”, 외부 시스템 가동 여부, 실제 저장 rollback은 채점하지 않는다.

## 사람이 따라 읽는 여정 3 — 날짜 경계·제한 공개·취소 우회를 놓치지 않기

1. 보고서 날짜 `점검일=2026-10-19, 작성일=2026-10-18`은 순서 위반이고, `작성일=2026-10-19`는 정상이다. 인계증 `인계일=2026-10-20, 회신기한=2026-10-20`은 위반이고, 기한 `2026-10-21`은 정상이다. 정확한 strict/inclusive 선언을 증거로 기록한다. field 순서 검사는 가능한 모든 행동 전후 상태의 증명과 다르다.
2. 일반조회자가 `열람제한=false, 상태=제출`인 IR-2404를 읽는 것은 허용, 같은 기록의 제한을 true로 바꾸면 금지다. `열람제한=false, 상태=정정대기`도 금지다. `열람제한=false, 상태=인계완료`는 허용이다. 검토담당자는 네 경우 모두 조회 가능하다. AND를 OR로 바꾼 누락, NOT의 범위를 잘못 둔 표현을 찾아낸다. 일반조회자의 수정·삭제, 인수담당자의 정정은 금지여야 한다.
3. 인계증 `발행, 인계방식=기록보관, 인계일=2026-10-20, 회신기한=2026-10-22`에 회신일 `2026-10-19`와 `2026-10-23`은 각각 금지, `2026-10-20`과 `2026-10-22`는 허용이다. 상태가 접수이면 같은 날짜여도 재접수는 금지다. 이는 입력한 날짜의 정책이며 시계·자동 기한 작업이 아니다.
4. 작성 화면에서 필수 입력을 비워 둔 채 취소를 따라간다. 시설 선택으로 돌아가야 하며 완료 화면 도착이나 일곱 field 획득 증거가 되어서는 안 된다. 정정/인계의 취소도 상세로 돌아간다. 등록 업무의 완료는 등록 제출 경로의 데이터 근거가 있어야 한다.
5. 운영중 시설만 공급하는 외부 호출자 전제와 내부 생성 권한을 구분한다. 운영중=false 시설은 이 전제 밖이며 현재 명세의 runtime이 운영 여부를 검증했다는 증거로 삼지 않는다. 외부 자료가 주어지지 않았을 때 문서가 가짜 시설/접수 자료를 생성하거나 자동 검색하는 것으로 보충하지 않는지 확인한다. “허용/자동 시도 선언이 있으니 실제 변경 성공/전체 조건 공간 안전성이 검증되었다”는 주장을 찾으면 경계 실패로 기록한다.

주요 coverage: R08–R12, R15, R22–R25, R29–R30, R36–R40. 필요한 것은 독립적인 사람이 읽을 수 있는 경계의 문서 증거다. 현재 statement runtime이 이 truth table을 실행해 증명해야 한다고 요구하지 않는다.

## 표현 대안과 오탐 방지

- 내부 stable ID, 별칭, 문장 제목과 화면 요소 ID는 달라도 된다. 역할·원본 입력·field 방향·조건·효과가 추적되면 된다. `E03-Rxx`는 평가 추적키이며 생성 문서에서 동일 주석 형식을 강제하지 않는다.
- NOT(제출 OR 인계완료)와 (NOT 제출 AND NOT 인계완료)처럼 동치인 금지 조건은 허용한다. 허용과 금지를 여러 역할별 문장으로 나누거나 다중 field Update를 한 블록/여러 블록으로 표현하는 것도 허용한다. 서로 다른 field/입력 변경을 중복 write로 오판하지 않는다.
- Can/Cannot의 효과 목록은 어떤 처리를 허용/금지하는지 식별한다. 그 목록 자체를 실제 수행으로 채점하지 않는다. DoAttempt에서 같은 조건과 효과를 반복하는 것은 중복 실행 보장의 증거가 아니다. 실제 mutation scheduler를 새로 만들 필요가 없다.
- 생성은 Action의 직접 enum 입력에 따른 각 값의 ExactlyOne 생성 결과로, 기존 기록 변경은 통합 문장으로 구분한다. 보고서는 결과, 요청은 요청종류, 인계증은 인계방식의 모든 값에서 하나를 생성하므로 업무적으로 종류에 따른 생성 거절은 없다. 이 direct enum 생성 결정을 통해 typed field producer를 연결할 수 있다. bare legacy Create에 field producer가 임의로 연결된다고 가정하지 않는다. R12의 운영중 선택대상 공급은 외부 전제다. R17/R20의 생성에는 기존 기록 상태 guard가 없고, 생성된 기존 요청/인계증을 R41/R42에서 다른 기존 입력과 대조하여 상태 변경을 시도한다. 이 준비→확정 구분을 보존해야 하며, 지원하지 않는 Create 효과를 통합 문장에 넣어 상태 guard와 결합했다고 주장하면 안 된다. 현재 compiler가 행동 실행을 막거나 원자적으로 저장한다고 주장하지 않아야 한다.
- 시설과 전송 접수 자료는 새로 생산하지 않는 외부 전제다. 이를 숨기기 위한 생성 화면/행동을 추가하면 R02/R06/R10 위반이다. 현재 legacy 화면 소비 분석은 외부 초기 데이터와 typed field producer를 연결하지 못한다. 이 한계는 보고서의 시설 복사값·초안 상태, 요청의 보고서번호·대기 상태·미처리 회신, 인계증의 보고서번호·초안 상태·미접수 메모, 사건으로 생산한 안내 필드에도 해당한다. 이 사실은 요구사항을 삭제하거나 사용자 입력으로 위장할 이유가 아니다. C의 중간본에서는 지원 문법으로 생산자·입력·화면 소비를 보존하고 실제 DATA-001/002 진단을 남긴다. 진단을 없애려고 표현 가능한 화면 조회를 설명문으로만 바꾸는 것을 개선 성과로 세지 않는다. 최종 한국어 명세에서는 두 군 모두 표·문장으로 동일한 출처와 조회 의도를 표현할 수 있으며, 이것은 최종 산출물의 형식 중립성이다. 컴파일 실패는 도구 결과에 그대로 기록하고, 최종 업무 의미의 정확도와 따로 보고한다. 분석기 연결을 개선할 필요가 있는지는 실제 진단과 원문 근거로 검토하며 모든 진단을 일괄 면제하지 않는다.
- 행동 전용 `새 본문`, `회신일` 같은 입력을 별도 저장 모델로 만들 필요는 없다. 기존 모델 field를 UI 입력의 의미에 연결하고 직접 typed Action 입력을 함께 보존하면 된다. 임시 UI state의 구체 구현은 채점하지 않는다.
- 보고서/요청/인계증의 문자열 번호는 식별 설명이지 Unique·관계·자동 join 요구가 아니다. 자동 번호 발급·중복 탐지·사용자 identity·정정 요청 개수 제약을 추가 요구하지 않는다.
- R38의 업무 분석은 초기 전제와 버튼 획득의 보수적 경로 계약이다. 실제 Action 성공이나 field 대입의 runtime 검증이 아니다. 등록 업무의 뒤쪽 상세/삭제/조건부 생성 경로 때문에 지원 범위의 unknown이 보고되어도, 그것만으로 저자 의미를 실패 판정하지 않는다. 별도의 미지원 경계 설명과 문서에 선언된 시작/완료/획득의 정확성을 평가한다.
