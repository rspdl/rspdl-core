# E01 비공개 평가표 — 접수부터 고객 인계까지 한 업무로 읽기

이 파일은 평가자 전용이다. 생성기에는 같은 디렉터리의 `input.md`만 제공한다. 평가 단위는 E01 제품 전체이며 아래 세 검토 여정은 서로 다른 독립 생성 과제가 아니다. 정답 RSPDL, 참조 구현, 테스트 코드, 의도적으로 결함을 심은 제품은 제공하지 않는다.

기준 소스 커밋은 **`837290a83911e160f27835f246a5bd7df21107b1`** 이다. 이 커밋의 현재 구현을 기준으로 지원 범위를 판정한다. 작성 중 저장소에 존재하는 다른 미커밋 변경이나 기존 제품 답안은 정답 근거가 아니다.

## 평가 단위와 증거 규칙

범위는 모델 5개, 필수 필드 18개, 화면 8개, 행동 8개, 역할 2개, 모델 내부 날짜 비교 2개다. 이 수는 점수 할당 목표가 아니다. 별도의 인계증 모델을 만들지 않고 5개 기록을 조회하므로 모델을 불필요하게 늘리지 않았다.

- 접수표 7필드: 접수번호, 고객명, 연락처, 기기명, 고장설명, 접수일, 수령희망일.
- 기기확인기록 2필드: 외관확인, 동봉품확인.
- 점검기록 2필드: 점검내용, 조치계획.
- 수리완료기록 4필드: 작업시작일, 작업완료일, 작업내용, 동작확인.
- 인계확인서 3필드: 수령인명, 반환물품확인, 인계일.

행동은 사전접수 조회, 방문접수 제출, 접수 확정, 점검 저장, 수리완료 저장, 인계 확정, 조회 중단, 방문접수 중단이다. 앞 여섯 행동은 성공·실패·시간 초과 결과가 있고 마지막 두 행동은 취소 결과가 있다. 업무시작의 두 경로 선택과 조회 실패 후 수기 전환은 이동 버튼이며 새 데이터 행동을 반드시 만들 필요는 없다. 같은 업무를 실제 사람이 역할을 바꾸어 이어가는 것은 문서의 의도다. 컴파일러는 사용자 로그인 전환이나 동일 실물 기기임을 증명하지 않는다.

공통 공개 산출물 계약과 평가자 지시의 판정 `충족 / 위반 / 판정 보류`를 따른다. 각 요구사항에 후보 명세의 근거 위치를 기록한다. ‘치명’은 주 흐름, 자료 출처, 권한 또는 완료 의미를 바꾸는 결함으로 영향 설명에만 쓰며 가중 점수는 없다. ‘일반’도 생략을 허용한다는 뜻은 아니다. 필요한 연결 일부가 없으면 위반이다. 예를 들어 실패 문구만 있고 정확한 재시도 수단이 없으면 누락 위반이다. 실질적인 해석 쟁점만 판정 보류로 남긴다. 정책을 발명하여 범위를 바꿔도 충족으로 보지 않는다. 입력을 반복하거나 ID를 나열한 사실만으로 통과시키지 않고, 공개 계약의 데이터 생애·행동별 계약·화면 연결 구조에서 실제 연결 근거를 찾는다.

문구·선언 순서·섹션 구성은 달라도 의미가 같으면 인정한다. 양쪽 모두 최종 한국어 제품 명세의 동일한 업무 의미를 심사한다. 중간 RSPDL과 compiler 로그는 평가자에게 주지 않으며 중간본을 근거로 최종 명세의 누락을 구제하지 않는다. 아래 문법 용어와 소스 지도는 사례의 표현 범위를 감사하는 자료이고 최종 명세에 RSPDL 문형을 요구하는 기준이 아니다. 정적 문서 검토이며 실제 소프트웨어를 조작한 결과로 보고하지 않는다.

권한의 자원 범위도 문서에서 확인한다. 다음은 R13의 행동 권한을 표현할 수 있는 한 가지 자원 연결 예시이며 유일한 정답이나 새로운 필드별 사업 정책이 아니다. 사전접수 조회는 접수표의 일곱 필드, 방문접수 제출은 접수표의 일곱 필드, 접수 확정은 기기확인기록의 두 필드, 점검 저장은 점검기록의 두 필드, 수리완료 저장은 수리완료기록의 네 필드, 인계 확정은 인계확인서의 세 필드에 관한 행동이다. 두 중단 행동은 접수표에 관한 행동으로 다루되 데이터를 변경하지 않는다. RSPDL에서 화면 권한을 증명하려면 해당 role/action/model/field의 명시적 tuple이 필요하며 모델만 적은 binding의 `Unknown`을 `Allowed`라고 보지 않는다. 권한 선언을 묶거나 나누는 구조는 자유지만 역할별 금지와 해당 화면의 허용 근거가 보존되어야 한다.

## E01-W01 — 첫 방문 고객을 접수하고 수리한 뒤 돌려주기

목적은 수기 경로부터 최종 인계증까지 제품 전체의 기본 업무가 읽히는지 확인하는 것이다. 실제 앱을 실행하지 말고 아래 값을 후보 명세의 폼·행동 입력·결과·화면·완료 의무에 대입해 문서상 근거를 따라간다.

1. 접수직원은 업무시작에서 ‘새 방문 접수’를 선택한다. 접수표는 `접수번호=V-261019-07`, `고객명=이소연`, `연락처=010-7421-6038`, `기기명=탁상용 선풍기 F12`, `고장설명=전원을 켜면 진동음이 큼`, `접수일=2026-10-19`, `수령희망일=2026-10-23`이다. 방문접수입력의 일곱 폼 항목과 제출 버튼을 찾아 제출 성공 후 접수확인 도착을 추적한다. 이 시점까지 뒷 단계 기록은 없다.
2. 접수확인에서 위 접수표를 조회하고 `외관확인=본체 우측 작은 흠집`, `동봉품확인=전원 어댑터 1개`를 입력한다. 접수 확정 성공이 기기확인기록만 생성하고 기사 화면으로 이어지는지 확인한다.
3. 수리기사는 점검기록에서 접수번호·기기·고장·외관·동봉품을 확인하고 `점검내용=날개 고정부 풀림 확인`, `조치계획=고정부 조임 및 회전 시험`을 제출한다. 점검 저장 성공 후 수리완료입력으로 간다.
4. `작업시작일=2026-10-20`, `작업완료일=2026-10-21`, `작업내용=고정부 조임 완료`, `동작확인=약풍·강풍 모두 진동음 없음`을 입력한다. 수리완료 저장 성공 후 접수직원의 인계확인으로 간다.
5. 접수직원은 접수·기기확인·수리완료 자료를 읽고 `수령인명=이소연`, `반환물품확인=선풍기와 전원 어댑터 1개 반환 확인`, `인계일=2026-10-22`를 제출한다. 인계 확정 성공으로 인계완료에 도착한다. 희망일보다 하루 빠른 인계를 금지하는 규칙은 없다.
6. 인계증에서 18필드가 모두 어디서 왔는지 역추적한다. 별도 인계증 저장 모델이나 완료 화면의 보충 입력이 없어야 한다. 두 역할의 허용 행동과 화면 담당이 일치하는지도 확인한다.

기대 증거: 단계별 폼·조회·생성·성공 이동·역할과 단일 완료 의무가 하나의 업무로 연결되어야 한다. 주로 R01–R10, R13–R17의 수기 외 공통 부분, R21, R24–R28, R31–R35를 검토한다. 외부 경로 R11–R12/R17의 구체적 증거는 여정 2에서 보완한다. 전화번호를 이메일로 바꾸거나 접수번호를 임의 자동 생성하거나 희망일을 납기 제한으로 사용하면 원문 보존 실패다.

## E01-W02 — 조회 중단과 저장 오류를 거쳐 기존 접수표로 끝내기

목적은 대체 진입이 같은 완료 의무에 합류하는지, 실패·시간 초과·취소가 각 원래 버튼에 연결되는지 확인하는 것이다. 아래 하위 시도는 같은 제품의 가능한 업무 기록 검토이며, 취소한 시도의 미제출 값이 새 업무로 넘어온다고 가정하지 않는다.

1. 외부 접수대장은 기존 접수표 `P-261018-12`를 선택해 전달한다. 값은 `고객명=박준호`, `연락처=02-318-9042`, `기기명=커피 그라인더 G4`, `고장설명=작동 중 멈춤`, `접수일=2026-10-18`, `수령희망일=2026-10-24`다. 먼저 업무시작에서 사전작성 경로로 간 뒤 별도 ‘조회 중단’을 선택한다고 가정한다. 취소 결과와 명시 복귀 경로가 업무시작에 닿고, 기존 접수표를 삭제하거나 완료 필드를 확보하지 않는지 확인한다.
2. 새 방문 접수로 들어가 `고객명=임시입력`, 나머지 값은 빈칸인 상태에서 별도 ‘방문접수 중단’을 선택한다. 이것도 취소 결과로 업무시작으로 돌아가야 한다. 방문접수 제출과 같은 버튼으로 묶여 있지 않아야 한다. 미제출 입력을 그 자체로 완료 자료로 취급하면 안 된다. 초안 화면값의 보존·폐기는 지정하지 않았으므로 어느 쪽도 추가로 요구하지 않는다. 사용자가 이후 필요한 값을 갖추어 명시적으로 다시 제출하는 것은 금지하지 않는다.
3. 새로 사전작성 경로를 선택한다. 사전접수 조회 실패를 따라가 ‘접수표를 확인할 수 없습니다’, 정확한 원래 조회 버튼의 재시도, ‘새 방문 접수로 전환’ 버튼을 확인한다. 전환 경로는 실제 방문접수입력에 닿아야 한다. 조회 실패 자체가 일곱 필드를 제공하거나 접수확인에 도착해서는 안 된다.
4. 같은 조회 버튼의 시간 초과를 따라가 지정 팝업과 자기 버튼 재시도를 확인한다. 이후 조회 성공을 따라가 선택된 기존 접수표의 일곱 필드가 명시적 조회 결과에서 제공되어 접수확인에 도착하는지 확인한다. 외부 record 입력이나 화면 READ만을 확보 근거로 삼으면 안 된다. 새 접수표 생성이나 고객 정보 재입력은 필요 없다.
5. `외관확인=외관 이상 없음`, `동봉품확인=없음`, `점검내용=안전 스위치 접점 오염`, `조치계획=접점 청소 후 동작 확인`, `작업시작일=2026-10-20`, `작업완료일=2026-10-20`, `작업내용=접점 청소`, `동작확인=세 차례 작동 정상`, `수령인명=박준호`, `반환물품확인=그라인더 본체 반환 확인`, `인계일=2026-10-21`로 공통 단계를 잇는다.
6. 점검 저장 실패 후 그 화면의 메시지와 동일 버튼 재시도를, 인계 확정 시간 초과 후 그 화면의 팝업과 동일 버튼 재시도를 확인한다. 다른 두 공통 저장 행동에도 실패/timeout 처리가 하나씩 있는지 문서 표나 선언을 대조한다. 수기 제출의 실패/timeout도 원래 수기 폼에 연결되어 있어야 한다. 문서가 같은 화면에 머무는 동안 입력을 확인·보완할 수 있다고 설명하는지 읽되 실제 메모리 보존이 검증되었다고 보고하지 않는다.
7. 인계 확정 성공 뒤 여정 1과 같은 18필드 완료 의무와 인계증을 확인한다. 성공 응답을 받지 못한 상태에서 실제 DB가 저장되었는지, 재시도가 중복 생성하는지는 이 평가로 판정하지 않는다.

기대 증거: R11–R12, R16–R23, R24–R35와 R05/R09/R10/R13–R15의 대체 값 근거. 여섯 주요 행동 각각에 성공·실패·timeout 처리가 연결되고 두 별도 중단 행동에는 취소 처리가 연결되어야 한다. 각 originating button별 handler와 복구 대상이 중요하다. ‘오류 시 재시도’라는 제품 전체 한 문장만 있고 어떤 버튼인지 확인할 수 없으면 R18–R19/R22/R29–R30은 누락 위반이다.

## E01-W03 — 같은 날 작업과 빠뜨리기 쉬운 완료 자료 확인하기

목적은 경계값을 임의 해석하지 않고 보존하는지와 필드 배치만으로 완료 자료를 얻었다고 오판하는지 확인하는 것이다. 아래 대입은 후보 문서의 판정 의도를 확인하는 것이며 결함을 심은 생성 프롬프트를 새로 만들지 않는다.

- 날짜: 접수일과 수령희망일을 모두 `2028-02-29`로 둔 접수표, 작업시작일과 작업완료일을 모두 `2028-02-29`로 둔 완료기록은 두 날짜 규칙상 허용이다. 수령희망일만 `2028-02-28`이면 접수표 규칙 위반, 작업완료일만 `2028-02-28`이면 완료기록 규칙 위반이다. `2027-02-29`는 유효한 날짜가 아니다. 날짜를 변경하여 자동 구제하거나 strict greater-than으로 같은 날을 거부하는 문서는 요구사항과 다르다.
- 출처: 업무시작에 외부 접수표 `P-280229-01`이 주어졌더라도 아직 조회 성공이 없다면 일곱 접수표 필드는 확보된 것으로 보면 안 된다. 같은 이름의 다른 모델 필드, 화면에 고객명을 표시한 사실, 실패 메시지를 완료 필수 데이터의 출처로 쓰는지 검사한다.
- 필수 입력: `동봉품확인=없음`은 유효한 명시 값이다. 동봉품확인 빈칸, 점검의 조치계획 누락, 완료기록의 동작확인 누락, 인계확인서의 수령인명 누락은 각각 필수 자료가 부족한 경우다. 접수표의 고객명이 이미 있어도 빈 수령인명을 대체하지 않는다. 후보 문서의 각 필수 선언·입력·제출·완료 의무를 찾아 이 구별이 설명되는지 확인한다.
- 권한: 접수직원이 점검 저장을 하거나 수리기사가 인계 확정을 하는 경우는 금지여야 한다. 반대로 수리기사가 점검을 저장하고 접수직원이 인계를 확정하는 경우는 허용이다. ‘본인이 맡은 건이면 예외’ 같은 조건을 넣거나 화면 환경 이름에서 역할을 추측하면 원문과 다르다.
- 경로: 수기 폼의 별도 중단 버튼, 외부 조회 실패, 점검 저장 실패, 인계 시간 초과의 각 끝점을 따라간다. 어느 것도 인계완료로 직행해서는 안 된다. 인계완료 도착 시 입력을 받는 구조로 이전 누락을 소급 충족하지 않아야 한다. 최종 화면의 18필드와 완료 필수 데이터 목록을 하나씩 비교한다.

기대 증거: R03–R15, R17–R23, R28–R35의 경계와 누락 민감성을 중심으로 확인한다. 여정 1·2와 합쳐 R01–R35 전체를 검토한다. 모델 내부 날짜와 필수 타입 선언은 정적 표현·검증 가능한 범위지만, 실제 저장 차단 UI를 작동시켜 확인한 것으로 적지 않는다.

## 오탐을 피하기 위한 허용 대안

- 같은 의미의 화면·버튼·모델 이름, 서로 다른 영문 stable ID, 합리적인 정보구조 구역명은 허용한다. 다만 여덟 역할별 업무 화면과 두 별도 중단 조작이 구별되어야 한다.
- 같은 화면 메시지/팝업의 추가 문구, 재시도 가능한 정확한 버튼을 별도 ID로 명시하는 방식은 허용한다. 사용자가 이해할 수 있는 지정 문구와 복구 대상의 의미가 보존되어야 한다. retry를 위해 새 화면이나 action을 억지로 늘릴 필요는 없다.
- 기존 접수표 READ는 여러 source-backed 조회 결과 선언으로 나누어도 된다. 일곱 필드 모두가 같은 조회 행동의 기존 접수표 입력에서 오고 성공 결과에서 채택되어야 한다. 여러 필드를 묶은 선언도 허용한다.
- 화면의 자료 조회 순서나 폼 묶음은 자유다. 필수 조회/입력이 빠지지 않고 완료 화면에서 입력으로 보충하지 않으면 된다.
- 실제 레코드 식별을 문자열 외래키나 자동 join으로 새로 구현할 필요는 없다. 명시적 기존 레코드 입력의 전달 의도와 같은 업무라는 설명을 보존하면 인정한다. RSPDL의 모델·필드 수준 확보 분석을 개별 record 정체성 증명으로 과장하지 않는다.
- input acquisition과 model creation을 각자 문서화한 것은 같은 저장을 두 번 했다는 뜻이 아니다. 구조적 생성 경로와 제출·성공 경로를 구별해서 판정한다. 실제 persistence, 저장 rollback, retry idempotence를 추가하지 않았다는 이유로 감점하지 않는다.
- 요구하지 않은 nullable 필드, 승인, 결제, 타이머, SLA, 고객 알림, 삭제 복구를 추가하지 않아도 된다. 통과를 위해 그런 기능을 추가하는 답변은 도메인 보존 관점에서 별도 기록한다.

### 특히 혼동하지 말아야 할 현재 구현 제한

`crates/rspdl-domain/src/analysis.rs`의 `analyze_workflows` 3694–3699행 및 `workflow_data_witness` 4437–4448행은 명시적 업무 입력획득을 같은 출발 버튼의 모든 목적 화면 경로에 적용한다. 이 입력획득 loop 자체에는 성공 outcome 조건이 없다. 그 뒤의 **제공 데이터** 전달만 성공 outcome을 확인한다(3700–3705, 4450–4455행). 비성공 outcome의 제공 데이터는 같은 파일 4145–4156행에서 거부된다.

따라서 이 제품은 제출과 중단을 별도 버튼·행동으로 두고, 제출 실패/timeout은 같은 화면 handler, 성공만 다음 화면으로 둔다. 이 구조의 경로·복구·제공 데이터는 정적으로 검토할 수 있다. 또한 action의 생성 mutation은 구조적 모델 생산자이고 frontmatter의 성공 handler는 화면 연결이다. 현재 core는 그 생성이 실제 실행되거나 성공 outcome에서만 실행된다는 것을 증명하지 않는다. R21/R25–R28의 성공 시 생성 의도는 반드시 보존하되 이 부분은 사람이 검토한다. ‘모든 input acquisition은 저장 성공일 때만 발생한다’는 일반 보장을 compiler가 증명한다고 적으면 안 된다. 입력 값이 폼에 남아 있다는 것, 실제 record가 저장되었다는 것, field availability가 정적으로 있다고 분석되는 것은 서로 다르다. R21–R23/R29–R31의 실제 저장 성공·실패 상태와 보존 동작은 사람이 업무 의미로 심사한다.

복구 target/path의 정적 검사는 `crates/rspdl-domain/src/analysis.rs` 5027–5178행과 위 action-outcome conformance에서 확인한다. 이것은 정확한 retry 버튼/return 경로가 handler에서 도달 가능함을 확인하는 계약이다. 사용자가 버튼을 반드시 누름, 요청 재전송 성공, 중복 저장 없음, 실물 반환 완료의 보장이 아니다.

### 사람 또는 별도 의미 평가자가 판정할 부분

자료 명칭과 필수 여부가 실무적으로 충분한지, 접수–기사–창구의 업무 인계가 설명 가능한지, 실제 같은 고객·기기·record를 끝까지 다룬다는 의도, 폼 수정과 오류 문구의 이해도, 본인 수령의 현실적 의미, 외부 자료의 실제 존재와 선택, 저장/재시도/세션/인계의 실제 실행은 사람 또는 별도 의미 평가자가 판단한다. 현재 컴파일러 통과를 일반적인 사업 품질·제품 완성·실행 성공의 증거로 사용하지 않는다. 통합 statement를 사용한 결과가 있더라도 compile은 참조·타입·명백한 내부 충돌 검사이며 행동을 실행하지 않는다. 미지원·Unknown은 성공으로 바꾸어 기록하지 않는다.
