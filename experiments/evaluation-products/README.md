# 제품 요구사항 작성의 평가용 사례 v1

**목적은 작은 모델이 제품 요구사항을 얼마나 정확하게 보존하는지, RSPDL을 쓰면 무엇이 달라지는지 평가하는 것이다.** 테스트 코드·정답 구현·명세 실행기는 만들지 않는다. 모델의 최종 기획 명세를 사람이 읽을 수 있는 근거와 함께 Sol 6.1이 평가한다.

현재 상태는 **평가 입력과 판정 기준 작성**이다. 생성 모델을 실행하지 않았으며 베이스라인 점수·개선율은 없다. 이전 `planning-value`와 `product-value`는 개발용 자료다. 이 폴더의 새 제품을 기존 수기 fixture의 통과율로 평가하지 않는다.

이번 평가는 제품 전체 요구사항을 처음에 한꺼번에 제공한다. 대화마다 요구사항을 추가·변경하면서 문맥이 늘어나는 상황을 측정하는 연속 평가는 포함하지 않는다. 이전 개발용 자료는 이번 PR의 포함 범위가 아니다.

## 다른 사람에게 설명할 제품 3개

제품 크기와 여정 제목을 한 장으로 설명하려면 [제품·여정 목록](case-catalog.md)을 먼저 읽는다.

| 제품 | 한 문장 설명 | 입력 | 평가자 전용 |
| --- | --- | --- | --- |
| E01 · 수리 접수부터 고객 인계까지 | 새 접수와 기존 접수가 합류하고, 실패·재시도 뒤에도 필요한 정보를 갖춰 수리를 마치는 업무 | [제품 요구사항](cases/E01-repair/input.md) | [판정 기준·여정 3개](cases/E01-repair/evaluator.md) |
| E02 · 교육 이수 증빙 발급과 정정 | 외부 이수 판정을 받아 증빙과 안내를 만들고, 조회·정정으로 연결하는 업무 | [제품 요구사항](cases/E02-training/input.md) | [판정 기준·여정 3개](cases/E02-training/evaluator.md) |
| E03 · 시설 점검 보고서 보완과 인계 | 역할·보고서 상태·입력 조건에 따라 변경 가능 여부와 실제 시도를 구분하는 업무 | [제품 요구사항](cases/E03-inspection/input.md) | [판정 기준·여정 3개](cases/E03-inspection/evaluator.md) |

각 제품은 **한 번에 전체를 주는 하나의 평가 입력**이다. 제품 안의 대표 여정 3개는 평가자가 문서의 연결성과 경계를 확인하는 읽기 순서다. 이를 독립 제품 9개나 실행 테스트 9개로 세지 않는다. 요구사항 수·화면 수만 늘리지 않고 서로 다른 진입·출처·결과·복구 경로를 연결한다. 모든 업무와 인물은 가상이다.

## 무엇을 전달하는가

- 생성 모델: 선택한 제품의 `input.md` 전체 + [공통 산출물·기준](public-contract.md) + 해당 실험군의 [작성 지시](generation-protocol.md). 파일 일부를 잘라 독립 질문으로 주지 않는다.
- RSPDL 사용군: 위 입력과 동결한 문법 문서·실제 도구 접근. 제품별 정답 예시는 제공하지 않는다.
- 평가자: 동일 제품의 입력·공통 기준 + `evaluator.md` + 익명화한 최종 명세 + [평가 지시](judge-instructions.md).
- 생성 모델에게 `evaluator.md`, `reviews/`, 다른 후보 출력, 점수, 기존 정답 fixture를 제공하지 않는다. 저장소 전체를 읽는 파일 도구도 주지 않는다.

공개 저장소에 있는 평가자 문서는 보안상 비밀이 아니다. 여기서 분리는 **실험 중 생성 입력에 넣지 않는 것**을 뜻한다. 학습 데이터에 없었다고 보장하지 않는다.

## 무엇을 측정하는가

제품별 요구사항 충족률, 중요 요구사항 위반, 여정별 끊김·모순, 근거가 불충분한 판정 수를 보고한다. 주 비교는 **동일 모델의 자체 검토 vs RSPDL 작성·진단 활용**이다. 문법 통과율은 별도 보조 지표이며 업무 명세의 정확도와 같지 않다. 계산식·실패 처리·재실험 규칙은 [실험 운영](generation-protocol.md)을 따른다.

문법·소스 검토는 평가 입력이 현재 표현 범위를 벗어나지 않는지 확인하는 작성 과정이다. 제품 구현을 실행하거나, 모든 요구사항을 컴파일러가 증명한다는 의미가 아니다. 특히 statement는 현재 compile-only다. 실제 저장·외부 전달·권한 집행을 검증했다고 쓰지 않는다.

## 검토와 변경 원칙

제품마다 Sol 6.1의 작성 담당, 문법 검토 담당, 평가 공정성 검토 담당을 분리한다. 동일 모델 계열의 독립 문맥 검토이므로 서로 다른 모델·사람 검토를 대체하지는 않는다. 검토 기록은 [reviews](reviews/)에 남긴다.

난이도를 맞춘다는 이유로 오류를 심거나, 지원하지 않는 기능을 필수 요구로 넣거나, 100% 결과를 임의로 낮추지 않는다. 모델 출력이 틀리면 프롬프트·코드·도구·품질을 개선하고 같은 기준으로 개선 전후를 기록한다. 입력이나 판정 자체가 잘못됐으면 근거를 공개하고 버전을 올려 **양쪽 실험군 모두** 다시 평가한다. 불리한 사례만 빼지 않는다.

첫 실행 전에 파일 해시와 모델·도구·예산을 고정한다. `content-manifest.json`은 작성 자료의 스냅샷이며 모델 실행 완료 기록이 아니다. 실행 조건은 [실행 기록 양식](run-record-template.md)에 반드시 채운다. 결과를 보고 개선에 사용한 제품은 이후 회귀 평가용이므로, 새 사례에 일반화됐다는 주장은 별도의 미사용 제품으로 확인해야 한다.
