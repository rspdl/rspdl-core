# 비교 실행 지시와 사전 고정 사항

아직 모델 실행은 하지 않았다. 이 문서는 이후 실행할 때 사용할 절차다. 기존 개발용 제품에서 문맥 길이와 출력 예산을 먼저 확인하고 아래 조건을 동결한다. 새 평가 제품의 점수를 보고 유리한 설정을 고르지 않는다.

## 주 비교: B 자체 검토 / C RSPDL 도구 활용

| 단계 | B · 자체 검토 | C · RSPDL 작성·진단 활용 |
| --- | --- | --- |
| 1차 호출 | 제품 전체와 공통 기준으로 명세 초안 작성 | 같은 입력으로 현재 문법의 RSPDL 초안 작성 |
| 중간 피드백 | 원래 입력과 자기 초안만 유지 | 실제 compiler 결과를 원문 그대로 제공 |
| 2차 호출 | 누락·모순·출처·분기·복구를 자체 점검하고 수정 | 같은 항목을 점검하고 진단을 참고해 RSPDL 수정 |
| 중간 피드백 | 자기 수정본 유지 | 수정본의 실제 compiler 결과 제공 |
| 3차 호출 | 공통 산출물 형식의 최종 한국어 명세 제출 | RSPDL 초안과 진단을 참고해 동일 형식의 최종 한국어 명세 제출 |

C의 두 compile 호출은 실패·미지원 결과도 그대로 기록한다. 사용자나 평가자가 오류의 정답을 대신 써서 전달하지 않는다. 최종 자연어 변환에서 누락되면 최종 명세의 오류다. 잘 작성된 RSPDL 중간본을 근거로 최종 출력에 가점을 주지 않는다. 실험 도중 compiler를 고치지 않는다.

지원 문법으로 표현할 수 있는 생산자·입력·화면 소비를 진단 제거 목적으로 지우거나 설명문으로만 바꾸지 않는다. 문법상 표현 가능하지만 분석기 연결이 부족한 경우는 원래 계약과 실제 진단을 보존한다. 컴파일 실패와 최종 업무 명세의 정확도는 별도 결과다. 이 문제를 수정하는 작업은 첫 실행을 보존한 뒤 새 버전의 개선 실험으로 진행한다.

두 군은 동일한 모델 revision·양자화·추론 설정·제품 입력·생성 호출 수(3회)·호출별 출력 상한을 사용한다. 실제 사용 토큰과 시간을 기록한다. C에는 문법 문서와 진단이라는 추가 입력 비용이 있으므로 총 입력 토큰까지 같다고 주장하지 않는다. 문맥 상한은 **더 긴 군의 전체 대화가 들어갈 수 있게** 사전 확인한다. 자동 요약·문서 자르기로 조용히 맞추지 않는다.

동결 문법 자료의 파일 목록·해시와 도구 명령을 실행 기록에 남긴다. 사례별 해설·평가 문서·정답 구현은 문법 안내에 포함하지 않는다. 실제 도구가 없는 실행을 “RSPDL 도구 활용” 결과로 기록하지 않는다.

기본 실행 계획은 제품별 **동일 seed 3쌍**이다. seed 숫자는 실행 환경 확인 후 실행 전에 기록한다. seed를 지원하지 않거나 결정론을 보장하지 못하면 이를 밝히고 순번을 맞춘 3회 반복이라고 쓴다. B/C 실행 순서는 제품·반복별로 교대하고 그 순서도 사전 기록한다. 제품 수는 3개이며 반복 3회가 제품 9개를 뜻하지 않는다.

이 비교로 말할 수 있는 것은 **RSPDL 작성과 도구를 포함한 전체 과정**의 효과다. 문법의 구조화 효과와 compiler 피드백 효과를 분리하려면 도구 없이 RSPDL만 작성하는 별도 비교군 D가 필요하다. D를 실행하지 않았다면 개선 전체를 compiler 덕분이라고 단정하지 않는다.

## 생성 모델에 주는 지시

공통: “첨부한 제품 전체를 대상으로 작업하라. 입력의 요구사항과 공통 산출물 기준을 보존하라. 빠진 정책을 추측하거나 평가자 전용 자료를 찾지 말라. 실제로 확인하지 않은 실행 결과를 만들지 말라.”

B 1차: “제품 명세 초안을 작성하라.”

B 2차: “초안을 원래 요구사항과 대조해 수정하라. 정상 경로뿐 아니라 다른 진입 경로, 데이터의 출처, 각 버튼의 결과와 복구, 허용·금지 조건의 모순을 점검하라.”

C 1차: “첨부한 동결 문법 자료의 지원 범위에서 제품을 RSPDL로 작성하라. 검사할 수 없는 의미는 누락하지 말고 검증 한계를 기록하라.”

C 2차: “실제 도구 진단과 원래 요구사항을 함께 검토해 수정하라. 정상 경로뿐 아니라 다른 진입 경로, 데이터의 출처, 각 버튼의 결과와 복구, 허용·금지 조건의 모순을 점검하라. 진단을 없애기 위해 원래 정책을 지우거나 변경하지 말라.”

공통 3차: “현재 작업을 공통 산출물 형식의 최종 한국어 제품 명세 하나로 제출하라. 요구사항 ID별 근거를 연결하고 미해결 사항을 명시하라. 작성 방식·모델명·compiler 점수·다른 후보와의 비교는 최종 명세에서 제외하라. 실제 업무 기능과 검증 범위의 한계는 보존하라.”

## 결과 집계

- 요구사항 충족률 = 충족 수 / 해당 제품 전체 요구사항 수. 위반·보류도 분모에 남긴다. 각각의 수를 함께 보고해 보류를 확정 오류와 구분한다.
- 제품별로 같은 반복의 C−B 차이를 퍼센트포인트로 기록하고, 세 반복의 값과 평균을 모두 보여 준다. 전체 요약은 제품별 평균의 단순 평균이다. 요구사항이 많은 제품이 전체를 지배하지 않게 한다.
- 중요 요구사항 위반 ID, 기능 사이 모순, 대표 여정 3개의 판정, 실제 토큰·시간·도구 실패를 함께 제시한다. 여정은 보조 읽기 검사이며 요구사항 분모에 더하지 않는다.
- 빈 출력·잘린 출력·문법 오류를 좋은 출력으로 교체하지 않는다. 남아 있는 최종 명세를 그대로 평가한다. 최종 명세가 없으면 요구사항은 모두 누락 위반이다.
- 요청 자체가 실행되지 않은 인프라 장애는 `실행 불가`로 분리한다. 장애 원인과 재시도 횟수(최대 1회)를 기록하고 같은 설정으로만 재시도한다. 지속 장애 쌍은 대응 차이 집계에서 제외하되 예정·성공·제외 개수를 모두 공개한다. 모델의 잘못된 명세나 compiler 오류는 인프라 장애가 아니다.

제품 3개는 소규모 파일럿이다. 요구사항·여정·반복을 모두 독립 표본으로 취급해 유의성을 과장하지 않는다. 100% 또는 악화 결과도 그대로 공개한다.

## 실패 후 개선

첫 결과와 그때의 코드·문서·모델 설정·파일 해시를 보존한다. 실패의 원인을 생성 오류, RSPDL 표현/진단 한계, 평가 입력·판정 오류, 인프라 문제로 근거와 함께 나눈다. 실패 위치에 맞춰 품질이나 코드를 개선하고 개선 후 결과를 새 실행으로 추가한다.

기준은 오류 수정의 목표로 유지한다. 단, 요구 자체의 잘못이나 실제 미지원 요구를 발견하면 아무 일 없던 것처럼 채점하지 않는다. 수정 사유·영향받는 요구사항·이전 판정을 공개하고 새 버전에서 양쪽 군을 다시 평가한다. 결과를 본 사례에서 좋아진 것은 해당 사례의 개선이며 미사용 제품에 대한 일반화 성과는 별도다.
